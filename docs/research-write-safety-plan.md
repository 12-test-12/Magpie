# 研究工作层写入收口方案

日期：2026-10-18。基线：本地提交 `0f0a38c`，0.28.0 / schema v18。

用户要求先完成修改方案，再实施；本批先确保已有数据和人工结论不会被随意覆盖。本文在业务代码修改前写入。实施与实际验证追加到主线二验收记录，不用方案代替验收。

## 1. 本批范围与顺序

1. Finding 研判与复测统一增加乐观版本检查，阻止旧窗口覆盖较新判定。
2. 关键人工结论必须填写依据；缺少关联复测证据必须如实显示，报告不能自动声称已由证据验证。
3. 总览摘要进入对应筛选结果，保持数量和业务范围一致。
4. 完成迁移兼容、事务回滚、跨项目、Undo/Redo、前端和本地隔离浏览器验收，同步文档与静态资源。

本批不实施 Finding 三维状态模型、JS 接入扩展、Notes 生命周期、任务报告扩展、搜索索引或性能重构。它们保留为后续独立工作包。Agent、Planner、Worker、调度器、自主探索、主动测试继续后置，不为它们预建数据表或执行入口。

## 2. 写入边界

| 数据 | 本批允许的写入 | 禁止的处理 |
|---|---|---|
| Entity、键、Observation、Relation、Contribution | 人工创建 Finding 继续经既有 ops/store 通道 | 不直接修改缓存事实、不修改身份/归一化、不自动合并或重定向资源 |
| 原始文件、Evidence | 继续引用项目内既有证据；现有人工作业保留原通道 | 不改写原文、来源定位、哈希，不伪造导入证据 |
| `finding_triage` | 经单写队列和事务校验后更新；版本随成功写入递增 | 不允许缺版本/旧版本覆盖，不回填历史依据或重判历史状态 |
| `finding_retests` | 通过当前 Finding 版本校验后追加一条人工记录 | 不修改旧复测；即使复测结论不确定也要递增版本，避免历史更新被忽略 |
| 人工审计 | 成功事务记录前后版本和本次决策 | 失败校验不遗留审计、复测或半条状态 |
| 测试数据 | 内存库或 `.magpie-dev/` 下新命名合成库 | 不使用真实项目做迁移、覆盖或破坏性测试 |

工作区已有 `dev.py` 行尾空白修改由用户保留，本批不顺带清理。没有远程推送、发布或分发包制作。

## 3. Finding 并发契约

- 只追加原子迁移 019，给 `finding_triage` 增加 `version INTEGER NOT NULL DEFAULT 1`；不修改 001–018。迁移仅增加版本元数据，逐表核对历史事实和人工判定不变。
- 从未人工处置的工具发现读取版本为 0；已存在研判行读取实际版本。详情响应 `triage.version` 返回版本；人工创建返回版本 1。
- 研判和复测请求必须携带 `expected_version`，且为非负整数。服务端不替调用者读取最新版本以绕过冲突。缺少版本返回请求校验错误，版本不匹配返回 409 `E_STALE_FINDING`。
- 同一事务内检查对象属于当前项目、未撤销、未合并，检查版本，校验决策，保存状态/复测、递增版本并写审计。不能在事务外完成检查后再无条件更新。
- 确定性复测维持现有状态联动；不确定复测保留原研判状态，只追加历史并推进版本。不把网络不可达等同修复。
- 前端两个写入口均使用已加载的同一版本。冲突时保留用户草稿并提示重新载入，禁止自动重试写入；对象/项目切换后的迟到响应继续受代次检查保护。
- Python ops 转发入口、合成生成器及测试调用同步迁移至显式版本，不能保留隐式无条件写入的后门。

## 4. 判定依据与报告

- 新建人工 Finding 默认为 `candidate`，前后端一致；选择其他关键状态时必须填写非空 `reason`。已有明确传入的关键状态也执行同一校验。
- 研判提交 `confirmed`、`resolved`、`false_positive`、`duplicate`、`inconclusive` 必须填写非空理由；`candidate` 允许留空。不通过关键词猜测理由真假，不自动认定为漏洞。
- 人工复测仍必须填写说明，证据关联仍可空缺；没有文件时可记录人工操作，但界面和导出明确标注“未关联复测证据，仅有人工说明”。证据 ID 必须属于同项目。
- 报告描述改为人工登记的判定与复测记录，分别输出有无关联证据和依据缺口。即使存在 Evidence 引用，也只说明有引用，不宣称系统验证了证据充分性或修复真实性。
- 历史无理由记录原样保留，在读取/导出时提示缺口，不伪造补齐，不批量改变其状态。原始数据与脱敏输出副本继续分开。

## 5. 总览跳转

- 已确认 → Findings `status=confirmed`；待核实 → Findings `status=candidate`，不继承另一状态的旧筛选。
- 待处理/进行中任务 → 人工任务 `status=open` 组合过滤；`open` 是只读过滤口径，不能写为任务状态，也不新增状态词表。
- 任务组合过滤总数/分页使用与总览相同的 `pending`、`in_progress`，并绑定游标。普通任务单状态筛选保持兼容。

## 7. 验收清单

| 场景 | 通过标准 |
|---|---|
| 两窗口研判 | A 保存后 B 的旧版本写入返回 409，A 的状态/严重度/理由保留，B 草稿保留 |
| 研判与复测交错 | 任一先成功，另一旧版本均被拒绝；不确定复测同样使旧版本失效 |
| 无理由/缺版本/跨项目/失效对象 | 明确拒绝，状态、历史、版本及审计均不变化 |
| 外层事务回滚 | 判定、复测、版本、审计一起回滚 |
| 报告 | 有证据/无证据/历史缺理由均如实输出，保留首次与历次复测来源；导出不修改事实 |
| 迁移 | v18→v19 不改事实/旧判定，新增版本正确；失败完整回滚；旧文件校验和不变 |
| 总览 | 点击两种 Finding 摘要与开放任务后，结果与计数同范围，无旧筛选残留 |
| 兼容 | 原有导入、Undo/Redo、项目隔离、有限分页与迟到响应回归通过 |
| 实际浏览器 | 用 dev.py 新命名合成库操作新建、判定、冲突重载、无证据复测、报告和摘要跳转；保存真实截图 |

最终运行 `check.py`、前端完整测试和生产构建，检查源代码/文档 diff。使用真实可用解释器并记录版本；没有实测不声称 Python 3.13 或严格性能契约已通过。
